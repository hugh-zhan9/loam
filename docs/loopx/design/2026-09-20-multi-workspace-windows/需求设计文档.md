## 窗口注册表

实现 [D-001](概要设计.md#D-001)、[D-002](概要设计.md#D-002)、[D-009](概要设计.md#D-009)。

```rust
pub const WORKSPACE_WINDOW_LABEL_PREFIX: &str = "workspace-";

struct WorkspaceWindowSession {
    label: String,
    /// canonical 根目录；窗口先创建、根目录后绑定时为 None。
    root: Option<PathBuf>,
}

pub struct WindowSessionRegistry {
    /// 按创建顺序保存，恢复顺序与 openWorkspaceRoots 的顺序都取自这里。
    workspace_windows: Vec<WorkspaceWindowSession>,
    last_focused_workspace: Option<String>,
    document_windows: BTreeMap<PathBuf, DocumentWindowSession>,
    document_error_windows: BTreeMap<String, DocumentErrorWindowSession>,
}

pub enum WorkspaceWindowClaim {
    /// 该 canonical root 已绑定在这个 label 上，调用方只应聚焦。
    Existing(String),
    Created(String),
}

pub enum BindOutcome {
    Bound,
    /// 查询与绑定之间被别的窗口抢先，调用方改为聚焦该 label。
    AlreadyOwnedBy(String),
}
```

方法契约：

| 方法 | 行为 | 边界 |
|---|---|---|
| `claim_workspace_window(root: Option<PathBuf>, requested_label: String) -> WorkspaceWindowClaim` | `root` 为 `Some` 且已被某 label 绑定 → `Existing`；否则登记 `requested_label` 并返回 `Created` | `root` 必须已 canonical 化；本方法不做文件系统访问 |
| `bind_workspace_root(label: &str, root: PathBuf) -> BindOutcome` | 把 `root` 绑到 `label`；该 label 原有绑定被替换（换工作区即重绑） | `root` 已属于**别的** label → `AlreadyOwnedBy`；属于自己 → `Bound`（幂等）；**label 不在注册表里 → `UnknownWindow`，不新增条目**。每个工作区窗口都先 claim 再构建，所以未知 label 只可能是窗口已销毁而它的上报还在路上；补一条会让某个 root 永远绑在不存在的窗口上，既留在恢复列表里，又对之后每次打开该文件夹都回答"已打开" |
| `workspace_root_for_label(&self, label) -> Option<&Path>` | 新窗口自报 session 时取回被指派的根目录 | 未绑定返回 `None` |
| `workspace_label_for_root(&self, root: &Path) -> Option<&str>` | 去重查询 | 按已 canonical 化的路径精确比对 |
| `open_workspace_roots(&self) -> Vec<PathBuf>` | 按窗口创建顺序返回已绑定的根目录 | 未绑定的窗口不出现在列表里 |
| `note_workspace_focus(&mut self, label: &str)` | 记录 `last_focused_workspace` | 只接受 workspace 角色的 label |
| `last_focused_workspace_label(&self) -> Option<&str>` | [D-009](概要设计.md#D-009) 的目标窗口 | 该窗口已销毁时回退到最早创建的工作区窗口；一个都没有才返回 `None`。回退而非直接 `None`，是因为 D-009 说"一个都没有才新建"——还有窗口时不该多开一个 |
| `remove_label(&mut self, label)` | 现有行为 + 移除 workspace 条目；若等于 `last_focused_workspace` 则清空 | — |

`role_for_label` 改为查 `workspace_windows`；`session_for_label` 的 workspace 分支带上根目录：

```rust
WindowSession::Workspace { root_path: Option<String> }
```

label 分配沿用 `lib.rs:502` 的 `WIN_ID` 计数器：`format!("{WORKSPACE_WINDOW_LABEL_PREFIX}{}", WIN_ID.fetch_add(1, SeqCst))`。与 document 窗口共用计数器不会碰撞，因为前缀不同。

### 新增的命令

```ts
// 纯查询 + canonical 化，不产生副作用。
invoke<WorkspaceOpenTarget>("workspace_open_target", { rootPath: string })
interface WorkspaceOpenTarget {
    canonicalPath: string;
    /** null = 尚未打开，可以询问用户 */
    existing: "current" | "other" | null;
}

// 聚焦已绑定该根目录的窗口。
invoke<void>("focus_workspace_root", { rootPath: string })

// 新建一个预绑定该根目录的工作区窗口。
invoke<void>("open_workspace_in_new_window", { rootPath: string })

// 当前窗口报告它打开了这个根目录（「当前窗口」分支与启动恢复都调用）。
invoke<BindWorkspaceRootResult>("bind_workspace_root", { rootPath: string })
interface BindWorkspaceRootResult {
    bound: boolean;
    /** bound 为 false 时给出，前端改为聚焦该窗口 */
    ownedByOtherWindow: boolean;
}
```

字段取舍：`workspace_open_target` 只回 `canonicalPath` 和 `existing` 两个字段，不回 label——前端不需要 label，给了反而让它有机会绕过注册表直接操作窗口。`existing` 用 `"current" | "other" | null` 而非布尔，因为两种命中对应不同结果（无操作 vs 聚焦别的窗口），布尔会让调用方再查一次。

错误语义：三个命令沿用 `WorkspaceError`。`canonicalize` 失败（目录不存在/无权限）→ `WorkspaceError`，前端按现有 `formatError` 提示，不弹二选一对话框。`focus_workspace_root` 找不到绑定 → 视为成功的空操作（窗口可能刚被关掉），不报错。

### 合并写入口

```rust
static STATE_WRITE_LOCK: Mutex<()> = Mutex::new(());

fn mutate_state_at_path<F>(path: &Path, mutate: F) -> Result<(), WorkspaceError>
where F: FnOnce(&mut AppState)
```

`mutate_state_at_path` 持锁完成「读 → 改 → normalize → 原子写」。**注意**：它不能调用现有的 `save_state_to_path`（`state_store.rs:218`），否则同一个 `std::sync::Mutex` 会重入死锁；需要先把其中的原子写部分抽成不加锁的私有函数，由两者共用。

四个写入点对应的命令与合并规则：

| 命令 | 合并规则 | 不触碰 |
|---|---|---|
| `save_workspace_state(workspace)` | 按 `root_path` upsert 进 `workspaces[]` 并提到队首；`recent_workspace_root = root_path`；若入参未带 `window_size` 则保留该条原有的值 | `preferences`、`open_workspace_roots`、其他 root 的条目 |
| `save_window_size(root_path: Option<String>, window_size)` | `Some` → 写进该 root 条目的 `window_size`（条目不存在则新建一条只含 `root_path` + `window_size` 的记录）；`None` → 写顶层 `window_size` | `workspaces[]` 的标签页与面板状态 |
| `save_app_preferences(preferences)` | 覆盖 `preferences` | `workspaces[]`、`window_size`、`open_workspace_roots` |
| `state_store::set_open_workspace_roots(roots)`（内部函数，非命令） | 覆盖 `open_workspace_roots` | 其余全部 |

`save_workspace_state` 保留 `recent_workspace_root` 的写入，是因为它仍是「`openWorkspaceRoots` 全部失效时」的回落目标（[D-006](概要设计.md#D-006) 第 3 条）。

### `open_workspace_roots` 的写入时机

由 `lib.rs` 在三处调用 `set_open_workspace_roots(registry.open_workspace_roots())`：

1. `bind_workspace_root` 成功之后
2. `open_workspace_in_new_window` 预绑定之后
3. `WindowEvent::Destroyed` 且 workspace 角色，**且注册表中还剩别的工作区窗口**

第 3 条的守卫**不能**用「应用是否正在退出」来判断。实现期核对 `tauri-runtime-wry-2.10.1/src/lib.rs:4126-4185` 发现：运行时先 `callback(RunEvent::WindowEvent{Destroyed})`，之后才在 `TaoWindowEvent::Destroyed` 里检查窗口表是否为空来决定发不发 `ExitRequested`。也就是说从 `ExitRequested` 置的标志，在 `Destroyed` 处理器里永远还是 false；而 macOS 从 Dock 退出走 `LoopDestroyed` → `RunEvent::Exit`，根本不发 `Destroyed`。

改用窗口计数：关掉多个中的一个 = 用户收窄了想要的集合 → 重写列表；关掉**最后一个** = 这个应用就是这样退出的（运行时在窗口表空掉时 exit）→ 不动列表。由 `should_update_restore_list_on_destroy(was_workspace, other_workspace_windows_remain)` 表达，见 `lib.rs`。

## 前端流程

### 打开文件夹

`chooseWorkspace`（`use-workspace-bootstrap.ts:122`）改为下列顺序，对应[概要的流程图](概要设计.md#D-003)：

1. `chooseWorkspaceRoot()` 返回 `null`（用户取消）→ 保持现有分支不动（`:132-140`）。
2. `workspace_open_target({ rootPath })`。
3. `existing === "current"` → 直接返回，不改状态、不提示。
4. `existing === "other"` → `focus_workspace_root`，当前窗口状态不变。
5. `existing === null` → 调用注入的 `confirmOpenTarget(canonicalPath)` 取用户选择：
   - `null`（取消）→ 返回，不改状态
   - `"new"` → `open_workspace_in_new_window({ rootPath: canonicalPath })`
   - `"current"` → 现有 `openWorkspace(canonicalPath)`，成功后 `bind_workspace_root`；若返回 `ownedByOtherWindow` 则改为 `focus_workspace_root`

`confirmOpenTarget` 由 `useWorkspaceBootstrap` 的入参注入，而不是让 hook 直接依赖 `useAppDialogs`。`AppDialogProvider` 在 `workspace-app.tsx:31` 包住的正是调用该 hook 的组件（`:38` 取 dialogs、`:51` 调 hook），注入在同一层完成；hook 因此可以在没有对话框 DOM 的情况下被测试。

对话框文案：

```
标题：在哪里打开这个文件夹？
正文：<canonicalPath>
选项：[当前窗口] [新窗口]    取消
```

`choice` 返回选项的 `value`（`app-dialogs.tsx:200`），取消返回 `null`——与第 5 步的三分支一一对应，不需要额外状态。

### 引导顺序

`useWorkspaceBootstrap` 的启动流程（`:153-227`）改为：

1. `load_app_state()` →（现状）读 preferences。
2. `get_window_session()`：`rootPath` 非空 → 打开它（新窗口与启动恢复都走这里），结束。
3. URL 带 `?workspaceAction=openFolder` → 走 `chooseWorkspace`（`workspace-app.tsx:384` 的既有处理不变）。
4. 否则 `recentWorkspaceRoot` 非空 → 打开它。
5. 否则弹目录选择器（现状 `:198`）。

第 2 步之所以排在 `recentWorkspaceRoot` 之前：被指派根目录的窗口必须打开指派的那个，否则启动恢复会让每个窗口都去开同一个最近工作区。

`openWorkspace` 成功后统一调 `bind_workspace_root`，让注册表与 `openWorkspaceRoots` 跟上。

### 窗口尺寸

- 恢复（`:181` `restoreTauriWindowSize`）：改为取 `workspaces[boundRoot]?.windowSize ?? state.windowSize`。窗口在这一步可能还没绑定根目录（第 5 步的空窗口），此时取顶层。
- 保存（`:291` `scheduleWindowSizeSave`、`:369` `persistCurrentWindowSize`）：改调 `save_window_size({ rootPath: 当前绑定的 root 或 null, windowSize })`。
- 四个 `saveAppState` 调用点（`:250`、`:286`、`:385`、`:418`）分别换成 `save_workspace_state`、`save_window_size`、`save_window_size`、`save_app_preferences`。`appStateRef` 仍然保留作为读缓存，但不再是写入的载体。

### 会话类型

`features/app/lib/app-session.ts:2` 的 `AppWindowSession` workspace 分支加 `rootPath: string | null`，`normalizeAppWindowSession`（`:25`）对非字符串一律归一为 `null`。`app-session.test.ts` 相应补用例。

## 验证与交接

### Verification Strategy

文档推演（本次交付的结果，非执行测试）：

**正常场景（AC-1 + AC-3，对应 TC-1/TC-3）**：窗口 A 开着 `~/notes`。用户在 A 按 ⌘O 选 `~/blog` → `workspace_open_target` 返回 `existing: null` → 弹对话框 → 选「新窗口」→ `open_workspace_in_new_window` 用 `claim_workspace_window(Some("~/blog"), "workspace-1")` 得到 `Created` → 建窗 → 新窗口 `get_window_session()` 得到 `rootPath: "~/blog"` → 打开并 `bind_workspace_root` → 注册表派生出 `["~/notes","~/blog"]` 写进 `openWorkspaceRoots`。推演结果与 AC-1、AC-3 一致。

**异常场景（AC-2 的失效根目录，对应 TC-6）**：`openWorkspaceRoots = ["~/notes", "/Volumes/ext/blog"]`，外接盘未挂载。按 [D-006](概要设计.md#D-006)：`~/notes` 恢复成功；`/Volumes/ext/blog` 跳过，同时从 `openWorkspaceRoots` 和 `workspaces[]` 中删除；`~/notes` 窗口顶部显示可关闭提示条列出该路径。推演结果与 AC-2 一致。此处的删除是**不可逆**的——盘重新挂载后该工作区按新工作区打开，没有标签页可恢复；这是 D-006 第 2 条明确接受的代价，实现时不得擅自改为保留。

**并发场景（D-004，对应 TC-4）**：窗口 A、B 分别绑定 `~/notes`、`~/blog`。B 先 `save_workspace_state(blog)`，A 后 `save_workspace_state(notes)`。两次都在 `STATE_WRITE_LOCK` 下重新读盘，A 的合并基于「已含 blog」的文件，结果 `workspaces` 同时含两条。与现状（图见概要）对比，blog 不再丢失。锁只保证互斥，不保证前端内存中的 `appStateRef` 是最新的——这正是「跨窗口偏好不同步」被列为非目标的原因，不是缺陷遗漏。

### Planning Handoff

已固定、实现不得自行更改：命令的请求/响应形状与错误语义、四个段的写者归属表、`openWorkspaceRoots` 的三个写入时机与退出守卫、去重先于对话框的顺序、失效根目录连同标签页状态一并删除（[D-006](概要设计.md#D-006) 第 2 条）、被推翻的四处既有测试的处置。

下游（实现时）可自行决定：具体文件拆分与函数命名、`ShutdownState` 用 `AtomicBool` 还是 `Mutex`、对话框的具体排版与按钮顺序、提示条组件的复用位置、Rust 单测的 fixture 组织方式。
