### 架构适配

| 需要 | 已有能力 | 判断 |
|---|---|---|
| 决定图片存到哪里 | `common/lib/image-storage.ts` 中的 `storeImageForWorkspace` / `storeImageForDocument`。它们是两个外壳唯一的存图入口 | 在这里扩展（[D-001](概要设计.md#D-001)），外壳和编辑器表面的存储契约不改 |

| 安全地写入含凭据的配置 | `llm_wiki_llm.rs` 中的 `save_llm_config_to_path` 及其私有辅助函数（约 180 行，错误码写死为 `llm_config_*`） | 抽成 `secret_config_file`，错误码前缀作为参数（[D-003](概要设计.md#D-003)） |
| 凭据只写不读 | `llm_config_update` 的 `preserve_api_key` 与 `llm_config_to_public` 的 `has_api_key` | 照这个形状做 |
| HTTP | `reqwest` 0.13，blocking + rustls，已经是依赖 | 复用。签名另需 `hmac` 0.12 |
| 不阻塞主线程 | `llm_wiki::run_blocking`（`spawn_blocking`） | 用同样的做法，`image_host` 中自己写一个等价的小函数，不跨模块引用 `llm_wiki` |
| 带超时运行外部进程 | `memory_agent_setup::run_with_deadline`，只适合少量输出 | 不复用。上传命令的输出没有上限，必须用独立线程读取（[D-008](#D-008)） |
| 向用户显示错误 | 表面已有的 `data-mdx-editor-mode-refusal` 提示条；`Toast` 的约定是"错误留在条中" | 表面新增同一种样式的图片提示条（[D-004](概要设计.md#D-004)） |
| 测试用的 HTTP 服务 | 没有 mock 服务依赖。`loam_cli.rs` 中有 `TcpListener::bind(("127.0.0.1", 0))` 的用法 | 测试里用 `std::net::TcpListener` 写一个最小的 HTTP 应答，不引入新依赖 |

职责归属：`image_host` 负责图床配置文件、校验和上传；`assets` 继续只负责本地 `.assets`；前端 `image-storage` 负责按配置分流；编辑器表面负责批次顺序和面向用户的提示。上传失败只影响当前这一批插入，不写任何本地文件，也不影响文档保存或草稿。

Support lenses：没有单独加载。架构适配按 architecture-conformance 契约写在上表。IPC 只供内部使用，没有触发 api-designer。

## 接口合同

<a id="D-012"></a>
**D-012 · Interface Contract · Accepted**：新增三个 Tauri 命令，在 `lib.rs` 的 `invoke_handler` 中注册。字段名在 wire 上用 camelCase（`#[serde(rename_all = "camelCase")]`），和现有命令一致。

| 命令 | 同步性 | 参数 | 返回 | 调用方 |
|---|---|---|---|---|
| `image_host_config_get` | 同步 | 无 | `PublicImageHostConfig` | 设置对话框；`image-storage` 每次存图前 |
| `image_host_config_update` | 同步 | `config: ImageHostConfigUpdate` | `PublicImageHostConfig`（保存后） | 设置对话框 |
| `upload_image_to_host` | **async**（`spawn_blocking`） | `name: String, bytes: Vec<u8>` | `{ url: String }` | `image-storage` |

`PublicImageHostConfig`：

```ts
interface PublicImageHostConfig {
  enabled: boolean;
  provider: "picgo" | "command" | "s3" | "github";
  picgo: { serverUrl: string };
  command: { command: string };
  s3: {
    endpoint: string; region: string; bucket: string; accessKeyId: string;
    pathStyle: boolean; pathPrefix: string; publicBaseUrl: string;
    hasSecretAccessKey: boolean;          // 替代 secretAccessKey
  };
  github: {
    owner: string; repo: string; branch: string; pathPrefix: string;
    customBaseUrl: string;
    hasToken: boolean;                    // 替代 token
  };
}
```

`ImageHostConfigUpdate` 和上面相同，但把两个 `has*` 换成"值 + 保留标记"：`s3.secretAccessKey: string` 加 `s3.preserveSecretAccessKey: boolean`，`github.token: string` 加 `github.preserveToken: boolean`。保留标记为 true 时沿用文件中的原值；为 false 时使用 trim 后的新值，空串表示清除。前端的计算方式和 LLM 设置相同：`preserve = hasExisting && input.trim() === ""`。

所有字符串字段在保存时 trim。`upload_image_to_host` 的 `name` 只用来取扩展名，扩展名校验复用 `image_extension`。不支持的扩展名报 `invalid_name`，和本地保存一致。

## 配置文件

<a id="D-013"></a>
**D-013 · Data Contract · Accepted**：配置文件路径是 `loam_home_dir()/image-host.json`，读写都通过 `secret_config_file`（[D-003](概要设计.md#D-003)），错误码前缀为 `image_host_config`。

- 文件不存在时 `image_host_config_get` 返回默认值。"不存在"是按跟随符号链接的方式判断的：只要哪里都没有这个文件，就是从没配置过，直接返回默认值，不做符号链接祖先检查。这样 `~/.loam` 是符号链接（例如同步的 dotfiles）时，图床关闭下的粘贴照常保存到本地（AC-1）。文件确实存在时，仍然做完整的检查；检查失败（路径上有符号链接）时，错误信息写明是哪个文件、为什么不读，因为每次粘贴都会在失败条中看到它。没有 HOME 时也没有 `~/.loam`，`image_host_config_get` 同样返回默认值（只针对 `loam_home_dir` 的 `asset_path_failed`）。默认值为：`enabled: false`、`provider: "picgo"`、`picgo.serverUrl: "http://127.0.0.1:36677/upload"`、`github.branch: "main"`、`s3.pathStyle: false`，其他字段为空串或 false，两个 `has*` 为 false。这时不创建文件。
- 所有结构体都加 `#[serde(default)]`：缺少的字段取默认值，未知字段忽略。`provider` 如果是未知值，读取时保留原串；在 `enabled: true` 时由校验报错，关闭时不影响任何行为。
- 解析失败（JSON 损坏）时 `image_host_config_get` 报 `image_host_config_load_failed`。这时 `image-storage` 按存图失败处理，不会当作关闭而悄悄改存本地。原因是用户开启过图床，按 R-2 不应静默写本地。顶层不是 JSON 对象（例如 `[]`）也算解析失败：serde 能按位置把数组读成结构体，而所有字段都有默认值，所以 `[]` 会被读成"已关闭"的配置。这是实现时由测试发现的。

<a id="D-014"></a>
**D-014 · Behavior Contract · Accepted**：校验器 `validate(config) -> Result<(), WorkspaceError>` 只有一份。`image_host_config_update` 在 `enabled: true` 时调用它，`upload_image_to_host` 每次都调用它。失败时报 `image_host_config_invalid`，message 形如 `missing required field: s3.bucket` 或 `invalid URL in s3.publicBaseUrl`，并写出字段路径，用于满足 AC-14。只校验当前 `provider` 的字段。

| provider | 必填 | 格式 |
|---|---|---|
| `picgo` | `serverUrl` | http/https URL |
| （所有地址字段） | — | `serverUrl`、`endpoint`、`publicBaseUrl`、`customBaseUrl` 不能含空白、`(`、`)`、`<`、`>`：它们会进入 `![alt](url)`，这些字符会让链接提前结束或损坏 |
| `command` | `command` 非空 | — |
| `s3` | `endpoint`、`region`、`bucket`、`accessKeyId`、SecretAccessKey（文件中已有或本次提供）、`publicBaseUrl` | `endpoint`、`publicBaseUrl` 是 http/https URL；`endpoint` 不能带路径、查询串或片段；`bucket` 只含 `[a-z0-9.-]` |
| `github` | `owner`、`repo`、`branch`、token（已有或本次提供） | `owner`、`repo` 只含 `[A-Za-z0-9._-]`，且不能是 `.` 或 `..`；`branch` 只含 `[A-Za-z0-9._/-]`，不含 `..`，不以 `/` 开头或结尾（Git 允许更多字符，但 `#`、`?`、`%` 会破坏 URL，`(`、`)`、`<`、`>` 会破坏插入的 Markdown 图片语法）；`customBaseUrl` 为空，或是 http/https URL |

S3 和 GitHub 的 `pathPrefix` 可以为空。非空时先去掉首尾的 `/`，然后每一段只能含 `[A-Za-z0-9._-]`，不能是空段、`.` 或 `..`。

<a id="D-006"></a>
**D-006 · Data Contract · Accepted**：对象键是 `{pathPrefix}/{sha256_hex(bytes)}.{ext}`。前缀为空时没有前导 `/`，`ext` 是 `image_extension(name)` 的小写结果。S3 和 GitHub 使用这个键。PicGo 和自定义命令使用 `{sha256}.{ext}` 作为临时文件名，远程怎么命名由它们自己决定。

## 接入方式

四种方式都实现同一个内部函数签名：`fn upload(&Config, &[u8], ext, timeout) -> Result<String /*url*/, WorkspaceError>`。`upload_image_to_host` 读取配置、校验，然后分派给其中一种。返回的 URL 必须以 `http://` 或 `https://` 开头，并且不含空白、`(`、`)`、`<`、`>`，否则报 `image_host_upload_failed`：它会原样写进 `![alt](url)`（源码模式下不转义）。

<a id="D-007"></a>
**D-007 · Interface Contract · Accepted · PicGo / PicList**：把图片写到一个新的临时目录（`tempfile::TempDir`），文件名按 [D-006](#D-006)。然后 `POST {serverUrl}`，`Content-Type: application/json`，请求体为 `{"list": ["<临时文件绝对路径>"]}`。响应 JSON 为 `{"success": true, "result": ["<url>", ...]}` 时取 `result[0]`。以下情况都报 `image_host_upload_failed`，message 中带上服务地址（去掉查询串和片段，PicList 的 key 在查询串里）：连接失败、HTTP 状态不是 2xx、响应不是 JSON、`success` 不是 true、`result` 为空。收到响应或出错之后删除临时目录（`TempDir` 被 drop 时自动删除）。如果 PicList 配置了鉴权 key，用户把 `?key=...` 写进 `serverUrl` 即可，不单独加字段。

<a id="D-008"></a>
**D-008 · Interface Contract · Accepted · 自定义命令**：

1. 按 [D-006](#D-006) 把图片写到临时目录。路径由 MDX 生成，只含临时目录前缀、十六进制和扩展名。如果路径中出现 `'`，直接报错不执行命令（做个断言，防止临时目录前缀里意外带了引号）。
2. 选择 shell：`$SHELL` 是绝对路径且文件存在时用它，否则用 `/bin/sh`。参数是 `["-l", "-c", "<command> '<临时文件路径>'"]`，其中 `-l` 让登录 shell 的 PATH 生效。stdin 设为 null，stdout 和 stderr 用 pipe。
3. 两个线程分别读完 stdout 和 stderr，每个流只保留最后 1 MiB（URL 在末尾）。主线程按 25ms 间隔调用 `try_wait` 直到超时。超时后 `kill` 子进程并 `wait`，报 `image_host_timeout`。命令退出后，最多再等 2 秒让管道关闭，然后取已经收到的输出：命令留在后台的进程可能一直占着管道。读取线程可能比这次调用活得久，直到那个后台进程退出。
4. 退出码非 0：报 `image_host_upload_failed`，message 带上 stderr 的最后 300 个字符（stderr 为空时用 stdout）。
5. 退出码为 0：从 stdout 中找最后一个以 `http://` 或 `https://` 开头、到空白或 `"'<>)` 为止的片段作为 URL（遇到 `)` 停止，是为了兼容自己输出 Markdown 的上传工具）。找不到就报 `image_host_upload_failed: command printed no URL`。
6. 结束后删除临时目录。

已知限制：`kill` 只结束 shell 本身，shell 启动的子进程可能继续运行。第一版接受这一点，不做进程组管理。

<a id="D-009"></a>
**D-009 · Interface Contract · Accepted · S3 兼容**：

- 请求：`PUT`，请求体为图片字节。地址有两种写法：
  - `pathStyle = false`：`{scheme}://{bucket}.{endpointHost}[:port]/{key}`
  - `pathStyle = true`：`{scheme}://{endpointHost}[:port]/{bucket}/{key}`

  MinIO 通常要用 path-style。AWS、阿里云 OSS、腾讯云 COS 用 virtual-hosted。R2 两种都可以，region 填 `auto`。
- 请求头：`Host`；`Content-Type` 由 `mime_type_for_extension(ext)` 得到；`x-amz-content-sha256` 是请求体 sha256 的十六进制；`x-amz-date` 格式为 `YYYYMMDD'T'HHMMSS'Z'`（UTC）；`Authorization` 为 `AWS4-HMAC-SHA256 Credential={accessKeyId}/{date}/{region}/s3/aws4_request, SignedHeaders=content-type;host;x-amz-content-sha256;x-amz-date, Signature=...`。不设置 ACL 头，是否公开由 bucket 策略决定（R2 不支持 ACL）。
- 签名：标准 SigV4。Canonical URI 对每一段按 RFC 3986 未保留字符做编码，`/` 不编码。查询串为空。签名密钥按 `kSecret → kDate → kRegion → kService → kSigning` 逐级 HMAC-SHA256 得到。签名函数接收任意一组已签名的头，所以能用 AWS 文档中的 S3 PUT Object 示例（含 `Date`、`x-amz-storage-class` 头）复现文档公布的签名。
- 响应：2xx 表示成功，URL 为 `publicBaseUrl` 去掉末尾 `/` 后加 `/{key}`。其他状态报 `image_host_upload_failed: S3 HTTP {status}: {响应体前 300 字符}`。S3 的错误响应是 XML，其中包含 `Code` 和 `Message`，原样截断即可。

<a id="D-010"></a>
**D-010 · Interface Contract · Accepted · GitHub**：

- 请求：`PUT https://api.github.com/repos/{owner}/{repo}/contents/{key}`，请求体为 `{"message": "Upload {sha}.{ext} from Loam", "content": "<标准 base64>", "branch": "{branch}"}`。
- 请求头：`Authorization: Bearer {token}`、`Accept: application/vnd.github+json`、`X-GitHub-Api-Version: 2022-11-28`、`User-Agent: Loam`。
- 201 或 200 表示成功。422 时，在同一个 60 秒预算的剩余时间内发一次 `GET .../contents/{key}?ref={branch}`（请求头相同）：返回 200 说明文件已存在，按 [D-006](#D-006) 内容相同，视为成功；否则报原来的 422。其他状态报 `image_host_upload_failed: GitHub HTTP {status}: {响应中的 message 字段，或响应体前 300 字符}`。
- URL：`customBaseUrl` 非空时为 `{customBaseUrl 去掉末尾 /}/{key}`（例如 `https://cdn.jsdelivr.net/gh/{owner}/{repo}@{branch}`），否则为 `https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{key}`。
- API 的基地址只在测试中可以替换（通过内部参数），不是用户配置。GitHub Enterprise 不在范围内。

<a id="D-011"></a>
**D-011 · Operational Contract · Accepted**：

- 超时：每次上传总时长 60 秒（常量 `IMAGE_HOST_UPLOAD_TIMEOUT`），一次上传发出多个请求时（GitHub 的 422 后续检查）共用这一个预算。HTTP 连接超时 10 秒。HTTP 超时和命令超时都报 `image_host_timeout`。测试可以传入更短的超时。
- 错误码：

| code | 场景 |
|---|---|
| `image_host_config_invalid` | 校验失败（[D-014](#D-014)） |
| `image_host_config_load_failed` / `image_host_config_save_failed` | 配置文件读写失败（来自 `secret_config_file`） |
| `image_host_disabled` | 调用 `upload_image_to_host` 时图床已关闭（查完配置到上传之间，其他窗口关闭了图床） |
| `image_host_upload_failed` | 网络错误、非 2xx、响应格式不对、命令失败、没有 URL |
| `image_host_timeout` | 超过总时长 |
| `invalid_name` | 扩展名不支持（沿用现有码） |

- 泄密防护：message 中永远不包含请求头、token、SecretAccessKey 或签名，只包含状态码、服务地址（PicGo）或 endpoint 主机名，以及截断后的响应体。代码中不对请求对象用 `{:?}` 打日志；含凭据的结构体（`S3Config`、`GithubConfig` 及两个 Update 结构）手写 `Debug`，凭据只显示为 `<redacted>` 或 `<none>`。
- 并发：多个窗口可以同时上传，彼此独立。配置文件只在设置保存时写入，通过原子替换完成，所以上传读到的一定是完整的旧版本或完整的新版本。

## 前端

<a id="D-015"></a>
**D-015 · Behavior Contract · Accepted · image-storage 分流**：`storeImageForWorkspace` 和 `storeImageForDocument` 的流程如下：

1. 调用 `invoke("image_host_config_get")`。
2. 如果 `enabled` 为 true，调用 `invoke("upload_image_to_host", { name, bytes })`，返回 `{ url, altText: name, storedPath: null, usedFallback: false }`。
3. 否则走现有的本地保存，命令、参数和返回值都不变。
4. 任何一步出错都直接抛出，不回退到本地保存（R-2）。

`StoredWorkspaceImage.storedPath` 的类型放宽为 `string | null`。生产代码中没有任何地方读取 `storedPath` 或 `usedFallback`（`grep` 结果只命中测试文件）。新建 `common/lib/image-host.ts`，放配置类型以及 `getImageHostConfig` / `updateImageHostConfig`，风格参照 `features/llm-wiki/lib/llm-wiki-client.ts`。它和 `image-storage.ts` 一样接受可注入的 `invoke`，方便测试。

<a id="D-016"></a>
**D-016 · Behavior Contract · Accepted · 表面的提示条**：`MarkdownEditorSurface` 新增 `onImageFailure?: (message: string | null) => void` 属性（`EditorStage` 的对应属性 `imageFailure` / `onImageFailure` 是必填的，状态由 `WorkspaceShell` 持有），以及内部状态 `imageProgress: { done, total } | null` 和一个按开始顺序记录进行中批次的 Map。表面组织失败文案，通过 `onImageFailure` 交给外壳；外壳用 `features/editor/components/image-failure-bar.tsx` 中的 `ImageFailureBar` 显示（[D-004](概要设计.md#D-004)）。`EditorStage` 在有标签和空状态两条渲染路径中都显示它。没有传 `onImageFailure` 的调用方，失败只写到 console，和改动前一样；两个产品外壳都传了。批次开始时调用 `onImageFailure(null)`。

- 进度：只显示粘贴目标就是当前屏幕上文档的批次；切换标签时重新计算。一批开始时加入 Map，并启动 300ms 定时器；定时器触发时如果这批还没结束，就把它标记为可显示，显示 `正在处理图片 {k}/{n}…`。一批结束（成功、失败或被拒绝）时从 Map 中移除。显示的是最近开始且已可显示的那一批；它结束后，如果更早的一批还在进行，就改为显示那一批；都结束时清除进度。
- 失败：`storeAndInsertImages` 在第 k 张（从 1 开始）`store` 抛错时停止本批，message 为 `图片未插入：{原因}`。一次多于 1 张时再加上 `（本次共 {n-k+1} 张未插入）`，这个数包括失败的那张和它之后的所有图片。原因取 `error.message`；如果 error 是字符串就用它本身；如果是带 `message` 的对象（Tauri 传来的 `WorkspaceError` 就是这种）也取 `message`；都不是就用"未知错误"。插入被拒绝时按拒绝码给出原因：`stale_document` 为"粘贴时的文档已不在编辑器中"，适配器返回的 `stale_revision` 为"文档已被重新加载或替换"，其他码为"编辑器拒绝了插入（{code}）"。批次自己的检查（两张图之间，文档被批次以外的改动修改了，最常见的是用户在上传下一张时继续输入）给出"插入过程中文档被修改"。都同样附上张数。现有的 `onCommandRefused` 调用保持不变。
- 显示：进度条在表面内，和 `data-mdx-editor-mode-refusal` 放在同一位置，`role="status"`；失败条在外壳内，位于内容区顶部，`role="alert"`，因为它是由用户操作引起的一次性事件。两者都带属性 `data-mdx-image-notice="progress|failed"`。失败条上有"关闭"按钮。下一次粘贴开始时清除旧的失败条。失败条不绑定某个文档：它说的是用户刚才那次操作，切换标签或关闭标签后仍然显示，直到用户关闭。
- 删除两处 `.catch(console.warn)`，改为由上述逻辑处理。`storeAndInsertImages` 自身不再向外抛错：循环中任何意外的异常（例如来自适配器的插入）也按失败处理，显示在失败条中。

<a id="D-017"></a>
**D-017 · Interface Contract · Accepted · 设置区**：`SettingsSection` 新增 `"imageHost"`，导航和内容区都加上"图床"。

- 控件：`Checkbox`（"粘贴或拖入图片时上传到图床"）；`SegmentedControl` 用于选择接入方式（PicGo / 自定义命令 / S3 / GitHub）；每种方式对应一组 `TextInput`，S3 另有一个 `pathStyle` 的 `Checkbox`。凭据输入框的占位文字在已设置时为"已配置，留空则保留"，和 LLM API Key 输入框用同一句话。区段放在单独的文件 `image-host-settings-section.tsx` 中，加载和保存由其中的 `useImageHostSettings` 负责，对话框只决定何时调用 `save()`。
- 提示文字：区段 hint 说明开启后图片会上传到图床、不再保存到 .assets、图片会离开本机、失败时不会改存本地。每种方式各有一句说明，例如 GitHub 下写明 token 需要 Contents 写权限，以及私有仓库的 raw 链接无法在编辑器中显示。
- 加载：打开对话框时与 LLM 配置一起调用 `image_host_config_get`。加载失败时（例如 JSON 损坏，按 [D-013](#D-013) 这会让每次粘贴都失败），在图床区顶部显示一条 `role="alert"` 的常驻提示，说明读取失败、在修好之前粘贴都会失败、保存会用下面的内容覆盖它。之所以不放在对话框的 `message` 位置，是因为那个位置 3 秒后自动清空，而这个错误要一直显示到被处理。图床区**仍然可以编辑**，以默认值开始，两个 `has*` 视为 false，所以凭据需要重新填写。保存后用新文件覆盖损坏的文件，这是在界面中修复它的唯一途径。
- 只在需要时写入：图床区当前内容和最后一次读到或保存的内容不同，或者填了凭据，保存才写 `image-host.json`；打开又关上开关、来回点接入方式都不算改动。配置读取失败时，只有用户在图床区操作过才写入修复，保存别的设置不会悄悄把一个损坏的配置替换成已关闭的默认值。否则跳过。每次粘贴都会读这个文件，而一个存在的文件要接受凭据文件的严格检查（路径上不能有符号链接），所以不能因为用户保存了别的设置就为从没用过图床的人创建它。
- 保存：在 `saveSettings` 中最先调用 `image_host_config_update`（需要写入时），失败就停止并显示 `formatError(error, "保存设置失败。")`，这时 preferences 和 LLM 配置都不写。成功后再按现在的顺序保存 preferences 和 LLM。保存后用返回值刷新图床区的状态，并清空凭据输入框。

### Planning Handoff

- **固定约束**：没有回退到本地（R-2）；凭据不出 Rust（D-002、D-012）；校验只有一份（D-014）；LLM 配置的错误码和行为不变（D-003）；本地保存命令的参数和返回值不变（D-015）；插入位置规则不变。
- **依赖顺序**：D-003 的抽取必须在 `image_host` 配置读写之前完成，并先确认现有 LLM 测试通过。D-012 的 wire 形状确定后，前端（D-015、D-016、D-017）和 Rust 的四种接入方式可以并行，二者只通过这三个命令耦合。
- **留给实现者决定**：`image_host` 目录内的文件划分（参照 `memory/` 目录）；组件和函数命名；中文文案的最终措辞，前提是保留上文给出的信息：原因、剩余张数、图片会离开本机。
- **实现后要更新的文档**：`docs/loopx/specs/editor.md` 中图片一节补充一句"存图失败会以提示条告知用户，不改变插入位置规则"。
- **不需要单独的计划文档**：本改动范围明确，按上面的依赖顺序直接实现即可。
- **未决**：无阻塞项。R-5（钥匙串还是 0600 文件）如果被否决，只影响 D-003 和 D-013。
